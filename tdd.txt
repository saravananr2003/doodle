Entity360 Technical Design

Account and Contact Master Data Management

Version 3.2  |  October 2 2026  |  DRAFT for review

Entity360 resolves first-party and third-party Account and Contact records into persistent, explainable identities, selects governed golden attributes and publishes consistent data to operational and analytical consumers. A cluster containing any current first-party member is a Customer; a nonempty cluster containing only third-party members is a Prospect. This rule applies independently to Account and Contact identity.

The confirmed initial integration is source-file ingestion from local disk. Internal application calls support the UI and processing; external consumer APIs and ADLS integration are deferred. Snowflake and Spark remain proposed mastering technologies from the reference design. Hosting services and control-store products are proposals, not approved requirements. The 1.5B resident-record target needs full-footprint benchmark evidence.

Mastering

Versioned mastering authority and transactional configuration, job and stewardship state. Snowflake, Spark and a transactional control store are proposed implementation choices.

Deferred integrations

Deletion

Immediately exclude a DELETED source identity, purge old evidence and repair its affected clusters before corrected publication.

2 1 Deployment constraints

Local disk is confirmed for source landing, not for the entire 1.5B corpus. Ingestion reads files on the designated host and bulk-loads accepted canonical evidence into the selected mastering authority; distributed workers consume that evidence and their approved work storage. Cross-host mounts, worker storage and distributed checkpoints require a deployment decision. An Azure staging service shall not be introduced as a hidden initial dependency. Proposed products must pass capacity, access and cost evaluation.

4 Canonical data and persistence

Every source identity is scoped by tenant, source, domain, namespace, source_record_id and identity_epoch. An epoch changes when a source key is confirmed recycled. Record versions contain event_time, ingest_time, payload hash, ROW_CREATE_TIMESTAMP, ROW_UPDATE_TIMESTAMP, ROW_STATUS, deletion marker and raw reference. Use 64-bit counters for volumes and globally unique immutable entity IDs. Namespace identifiers and preserve postal and ID leading zeros.

5 Local disk ingestion and standard record contract

Global Configuration stores base_directory, configuration_revision, validation_status, changed_by and effective_at. Source configuration stores incoming_directory, processing_directory and reject_directory as paths beneath the canonical base. Validate traversal, symlink escape, overlapping assignments and read/write permissions. A run pins its configuration revision; changing the base never silently relocates active work.

The directory tree is illustrative; names are administrator configured. Confirm completed file delivery through an agreed marker, producer rename or verified stability policy. Claim files with a transactional lease and atomic rename where supported. If the filesystem cannot atomically move across locations, use validated copy, checksum and ledger-controlled handoff. Do not assume cross-volume move atomicity.

The delivery ledger records source, identity, checksum, file location, schema, extraction watermark, pinned configuration, stage counts and checkpoints. Content hashes suppress unchanged replay within source identity; equal payloads with distinct source IDs retain independent identity. Keep local file payloads out of unrestricted logs. Rejected rows and reasons go to the source reject directory. Successful-file archive or removal policy remains an open operating decision; no extra required archive directory is assumed.

Adapters explicitly define whether incoming columns are mapped or Entity360 technical columns are populated on ingestion. Missing upstream deletion semantics cannot default silently to ACTIVE. Maintain the columns on current source, canonical and golden row contracts. Removal leaves a minimal tombstone with DELETED and technical timestamps, not a retained payload of deleted attributes. All timestamp definitions are Entity360 technical timestamps unless separately named source timestamps.

For full snapshots, validate completeness before producing deletions. Source sequence or event time controls newer-versus-older facts. Unknown order and equal-time conflicts require deterministic source policy or review; arrival time alone does not override a newer deletion. Disabling ingestion does not remove accepted memberships.

5 1 Deleted source identity processing

Key the exclusion by source_system, entity_type and source_id, extended with namespace and identity epoch where required. Accept the deletion and persist a minimal watermark, then apply that exclusion to candidate generation, scoring, clustering, survivorship, UI evidence and export reads before asynchronous physical purge completes. Concurrent runs carrying an earlier exclusion revision cannot publish obsolete evidence.

Find affected components, accepted memberships, assertions, golden winners, hierarchy and affiliation endpoints and historical derived artifacts before removing evidence.

Purge current and historical source payloads, aliases, features, postings, candidate decisions, edges, membership contributions and cached copies for the identity. Sanitize source-only values from current and historical goldens and relationship evidence.

Remove that member and affected edges; recompute components from remaining valid evidence. A deleted bridge may split an entity. Preserve justified surviving IDs and record corrected successor mappings.

Recompute survivorship, relationships and source counts. Any first-party member means Customer; third-party-only means Prospect; no valid members means retired.

Build and validate corrected publication artifacts. Internal readers obey the exclusion overlay even while remaining on an older release; never expose removed evidence during repair.

Publish correction, split, delete and class-change events or dataset deltas to configured consumers. Reconcile affected counts and verify that no deleted-only value remains.

Purge or sanitize raw and reject rows, processed-file copies, history, indexes, caches and model-training snapshots containing the source identity. Mixed delivery files may require rewriting a sanitized copy or removing the copy under the approved retention policy. Retain minimal deletion audit without reusable source attribute content. Backups are blocked from serving until deletion markers are reapplied; backup expiry and downstream-copy correction timelines require operational approval.

Older replays and restores cannot reinstate a deleted identity. Reactivation or confirmed source-ID reuse requires a separately approved identity-epoch policy; this draft does not automatically interpret an ACTIVE row arriving later as authorization to undo deletion. Test exclusion during in-flight jobs, failed purges and restoration. A purge failure remains visible and retriable while the identity stays excluded.

6 Standardization and data quality

Account transformations retain original values and normalize case, Unicode, spacing, legal suffixes, address directionals, street components, units, postal forms, domain and phone. Generate country-aware name prefixes, phonetic keys, street-number keys, PO-box flags and approved name-address expressions. A PO box is not a physical Site; a shared building is not a shared business.

Contact transformations parse names and aliases, classify personal, business and role-based contact points, preserve email local-part semantics conservatively and use country-aware phones with extensions. Provider-specific email normalization requires explicit validation. Missing values never become invented identifiers. Deleted identities are excluded before all feature and candidate paths, including historical aliases. Shared switchboards and inboxes are weak evidence, not person identifiers.

Quality controls score validity, completeness, freshness and consistency per field and record. Invalid values cannot win survivorship just because the source has higher priority. Expressions run in a restricted structured evaluator, with syntax, type, cardinality and resource checks; do not execute administrator text as arbitrary Python or SQL. The same fixtures verify transform parity across Spark, warehouse and online features.

7 1 Account and Contact retrieval

Maintain partitioned key postings against the complete resident evidence corpus. Each changed record searches both same-run changes and accepted resident records. Deduplicate unordered pairs by canonical endpoint ordering and evaluation version, while retaining every candidate origin. Never load the global key index into one driver. Null or empty keys create no posting.

Oversized blocks are subdivided using additional compatible features. Remaining difficult blocks enter a deferred queue or a measured secondary strategy. Caps are recorded by source and rule; a top-K truncation cannot silently become a completed non-match. 7 2 Feature scoring and decision

Features include exact identifier agreement, Levenshtein and token similarities, phonetic and alias evidence, address components, unit and country, domain and phone, source agreement and conflicting strong identifiers. Contact features add ownership periods, name evidence and affiliation corroboration. Repeated vendor copies are not independent consensus. Missingness treatment and weight normalization are part of the immutable policy bundle.

Separate Account and Contact models and thresholds are required. The initial rule engine supports numeric weights, compound conditions, scoped gates, AND or OR groups, directional source conditions and hard contradictions. Example Account T_auto 0.95 and T_review 0.85 are provisional configurations, not universally safe operating values. Calibrate on labeled holdouts before promotion.

if evaluation_incomplete: processing_status = "INCOMPLETE"

elif score >= T_auto and all_eligibility_gates:

    match_status = "MATCH_FOUND"

elif score >= T_review or conflict_requires_review:

    match_status = "CANDIDATES_FOUND"

else: match_status = "NO_MATCH"



Retain candidate origins, feature contributions, reason codes, score type, policy and model version, audit_id and evidence time. A probability claim is permitted only for a calibrated model output; a weighted rule score is labeled as a score. A dependency failure returns an operational error, never NO_MATCH.

8 Constrained clustering and persistent identity

Use distributed candidate edges and explicit constraints to propose compatible connected components. Transitive connectivity alone is insufficient: if A matches B and B matches C but A contradicts C, reject or review the proposed union. Evaluate grain, strong-identifier conflicts, cannot-link constraints, giant-component limits and temporal channel ownership evidence before activating membership. Components that exceed safe budgets remain pending with visible coverage impact. Apply the source-specific pair policies and prospective-cluster cardinality checks in section 25 before accepting any union, including transitive and incremental unions.

Stable IDs are reused when the accepted member identity continues. A true merge retains the approved established survivor, writes retired-ID redirects, remaps relationships and publishes merge events. A split assigns corrected memberships and stable IDs under a documented survivor policy; a prior ID can resolve to a split event with multiple successors rather than silently choosing an arbitrary person. Historical lineage remains available.

A changed record seeds affected neighborhoods; edge insertions can merge components, while deletions can split them. Expand impact across partition boundaries until the component boundary is proven. Recompute memberships, goldens, affiliations, classification and projections together. If safe incremental repair cannot be bounded, defer the impacted component or shadow rebuild it. Do not publish a partial repair as a final identity.

Durable steward decisions are versioned constraints, never overwritten by a refresh. Overlapping repairs use component leases and expected base versions; conflicting runs retry from the latest accepted component state. Global policy changes use a shadow full rebuild, ID migration comparison and approved activation. Match-only and test modes write diagnostic outputs without changing active identity.

9 Customer and Prospect classification engine

The finalized business rule is a direct membership aggregate, independent of match score, surviving source, activity and relationships. Count current eligible nondeleted source identities once each at the entity grain. An accepted member counts even if some of its attributes are null or invalid. Source categories must be valid before publication; an unknown category quarantines or blocks the affected output rather than defaulting to Prospect.

fp = count(distinct eligible member with category FIRST_PARTY)

tp = count(distinct eligible member with category THIRD_PARTY)

if fp > 0: entity_class = "Customer"

elif tp > 0: entity_class = "Prospect"

else: lifecycle = "RETIRED"  # no current Customer or Prospect output

10 Survivorship hierarchies and affiliations

An assertion is eligible only if source rights, validity, field quality and lifecycle permit use. A configured coherent survivorship group selects exactly one eligible source-record version; all group values come from it, including null values. Different groups may choose different source rows. Ordered waterfall steps, anchors, source priorities, frequency, business recency and deterministic tie-breaking follow the versioned policy described in section 22. Keep winning reasons and permitted nondeleted losing assertions within retention; DEL rules override retained history.

Typed hierarchies separate legal ownership, ultimate parent, operating structure and commercial bill-to or ship-to. Prevent invalid cycles in tree views; multiple valid views are allowed. Parent changes and acquisitions do not automatically merge entities. Contact affiliations carry employer, Account, Site, role, confidence and valid intervals. A job change need not create a new person; uncertain employers remain unresolved. Multiple simultaneous affiliations are allowed.

Primary email, phone and address are selected separately from permission. First-party suppression and permitted purposes dominate contact delivery. Vendor facts cannot overwrite authoritative ownership, transaction facts or permissions. Steward overrides carry scope, reason, approver and expiry; fresh conflicts prompt review rather than silently deleting an override.

11 Publication consistency and distribution

Prepare immutable release R from base publication B with evidence watermark, registry, policy and model versions. Stage canonical, membership, golden, xref, relationship and classification outputs.

Reconcile uniqueness, referential integrity, member counts, classification, totals, merge and split redirects, entitlements and history. Build required internal query generation R; verify row counts and checksums.

Mark all required artifacts ready. Activate R with compare-and-swap on the active manifest only if B is still current. A conflict rebases or retries; no concurrent run overwrites another release.

Every internal request pins one manifest and uses its matching projections. Warehouse and export readers resolve the same release explicitly. Do not independently swap unrelated current tables and advertise a globally atomic release.

Publish outbox events and consumer manifests only after activation. Idempotent events use event_id, entity_id, entity_version, release_id, operation, prior and new class, changed fields and policy version.

Consumers acknowledge watermarks, deduplicate event IDs and reconcile to a full snapshot at that publication. Handle merge, split, delete, suppression and class-change events explicitly.

There is no distributed transaction across PostgreSQL, Snowflake and serving stores. Immutable artifacts plus a single logical activation pointer provide a release fence. Internal application and export services consult the active manifest; warehouse clients use a release resolver or receive an explicit publication_id. During lag or outage, consumers remain on the previous complete release and report its age. Derived projection lag is monitored rather than hidden.

Urgent deletion and suppression use an independently versioned deny policy evaluated at delivery time, so an older pinned release cannot expose newly prohibited fields. Update or invalidate caches and delivery projections promptly. Backups and restored releases reapply the deny ledger before serving. Previously downloaded files require consumer correction and acknowledgment; the platform cannot silently revoke an offline copy.

12 Internal integration boundary

Initial internal services support application configuration, job control, stewardship and entity exploration. API endpoint definitions, schemas, authentication contracts, status codes, health routes and deployment details are specified in API Technical Design Document. External consumers have no initial search, matching, enrichment or Customer and Prospect lookup interface. The core mastering design supplies service-level data and consistency responsibilities without duplicating API specifications.

13 Stewardship administration and policy release

The UI retains login, source and file configuration, canonical groups and attributes, source mappings, standardization, blocking tests, algorithms and thresholds, grouped and directional match conditions, source priorities, waterfall survivorship, batch and stage history, golden and source exploration, xrefs, hierarchy, affiliations, duplicates, review and configuration audit. Results use server-side pagination, bounded exports and field-level authorization.

Review actions include confirm or reject identity, must-link or cannot-link, merge or split, attribute override, affiliation correction and escalation. A decision records evidence version, expected case revision, actor, approver, reason and scope. Bulk changes require a preview of affected identities and consumers. Administrator, Analyst and Viewer remain supported; Steward, Approver, Operator, Consumer and Auditor capabilities are explicit grants.

Promote policies as immutable bundles through development, test and production. Validate schema, referenced fields, expression safety, contradictory rules, holdout outcomes and blast radius. A running job pins its starting bundle. Rollback restores a policy version and invokes the required affected backfill; it does not magically undo already published identities. Review constraints and privacy decisions remain effective unless separately superseded.

14 Processing health observability and operations

Monitor base and source directory accessibility, free disk, complete-file detection, file claims, queue age, rejects, source freshness, stage latency, skew, spill, failed jobs, deletion backlog, cluster repair and publication age. Track delivery_id, run_id, partition_id and publication_id without logging unrestricted source attributes. Internal API probes and transport contracts are defined in the separate API design.

Alerts cover inaccessible directories, low disk capacity, schema changes, unexpected delete volume, classification shifts, deferred blocks, failed releases, stale policies and missed purge deadlines. Runbooks support pausing sources, correcting rejects, resuming checkpoints, repairing clusters and rebuilding derived artifacts. Operational status shall report service health separately from data freshness.

15 Scale workload and capacity model

The target is 1.5 billion simultaneously resident logical source records across Accounts and Contacts. Historical versions, candidate edges, memberships, raw files, goldens, relationships, audit and backups are additional. Size by record width, source multiplicity, change rate, candidate fan-out and graph impact, not by record count alone. All-pairs comparison would produce about 1.125 quintillion pairs and is excluded.

Partition by stable source identity for reads and key namespace or hash for postings. Avoid daily partitions alone for point retrieval.

For each storage surface, estimate count × observed bytes × retention or history factor × replication factor, then add measured index, backup and compaction costs. Candidate evidence may dominate; retain required decision lineage and sample diagnostic nonmatches under an approved policy. Do not specify a fixed cluster size without measured work distribution. Batch and online compute have separate quotas and failure domains.

16 Security entitlements deletion and recovery

Use enterprise SSO and managed service identity, private connectivity where supported, least-privilege scopes, encryption in transit and at rest and approved secret rotation. Authorize UI, API, warehouse, exports and evidence drill-down consistently. Field-level permitted purpose, vendor license period, Contact suppression and country rules are policy assertions evaluated on output. Merging cannot broaden permission.

Retention schedules cover raw deliveries and retained nondeleted canonical and golden history, match evidence, labels, candidate stores, caches, exports and backups. Deletions propagate tombstones, invalidate projections and publish consumer corrections; preserve only permitted minimal audit evidence. Legal holds and exceptions are explicitly governed. Purge acceptance reconciles active surfaces, and restore tests reapply tombstone and deny ledgers before enabling serving.

Checkpoint immutable partitions, use bounded retry with backoff, quarantine persistent errors and protect mutations with idempotency keys and version checks. The outbox relay offers at-least-once delivery; consumers deduplicate, rather than assuming end-to-end exactly-once network transport. Backups coordinate control state, manifests and authoritative data watermarks. On recovery rebuild compatible serving projections, reconcile IDs and counts, then reopen traffic.

17 Learned matching and recommended expansion

Phase 2 adds separate supervised Account and Contact models, active-learning case selection, monthly refresh evaluation and conditional retraining. New UI-selected fields enter a proposed feature set and trigger impact tests. Feature, label, training snapshot and model versions are immutable; prevent label leakage across train and holdout identities and treat steward judgments as evidence with quality review. Promotion requires precision, retrieval and cluster quality, drift, explainability, serving parity and rollback gates.

CDC and event ingestion add source ordering, lateness and reconciliation after core delta correctness passes. Match-before-create needs a separate concurrent-create fence or enterprise workflow reservation; a read-only lookup alone cannot prevent two simultaneous CRM creations. Governed writeback verifies expected source revision, field authority, approval, idempotency and acknowledgments, and tags provenance to prevent echo loops.

Phase 3 can evaluate multilingual embeddings, geospatial support, external channel validation and AI-assisted mapping or review. Treat untrusted source text as data; AI suggestions cannot execute tools or publish policy without validated structured review. Inferred potential, personas or enrichment are labeled and never fabricate source facts or change Customer or Prospect classification.

25 3 Effective pair policy and exact conditions

Resolve the effective source-pair policy from the pinned release before evaluating pair evidence. Preserve direction where required; symmetric policies apply in both orientations. Proposed precedence is explicitly ranked specificity and configured priority, with ambiguous equally ranked policies rejected at activation. The resolved policy consists of mandatory gates and qualifying clauses. Evaluate applicable mandatory gates across every match path; only then evaluate the configured qualifying Boolean expression or score route. A general fuzzy rule, exact-identifier route, another OR branch or model score cannot override a mandatory source-specific gate. Any approved exception must be explicit policy metadata.

For the illustrative MDR-versus-MDR policy, configure name and address exact comparison gates by field ID. Exact equality operates on the selected raw or normalized canonical representation and its preprocessing release; the user must choose the representation. It is distinct from SCORE_EQ 1.0 for cosine or Jaccard, because a full similarity score need not imply equal strings. For MDR-versus-DNB or MDR-versus-Salesforce, configure fuzzy algorithms, tokenizers and individual field thresholds in separate policies. No fuzzy percentages were supplied for these source pairs; none are assumed. Unsupported or missing policies produce visible unresolved cases, not implicit matching permission.

25 4 Prospective cluster validation

Pair compatibility and cluster admission are separate decisions. For each proposed union of clusters A and B, build the prospective distinct current membership A union B, including same-run accepted additions. Evaluate every applicable constraint against that prospective membership, not just the joining pair. For a configured source S, count distinct namespaced logical source identities in the target entity domain. Source versions and repeated deliveries of the same identity do not count as additional members. The conditional source-presence predicate is evaluated on the complete proposed cluster; when it holds, count(S) must be at most the configured maximum.

If the MDR cap is one, union of a cluster containing MDR-A with any cluster containing MDR-C fails when A and C are different current source IDs. This remains true when the joining edge is DNB-to-Salesforce or when a long path contains no direct MDR-to-MDR edge. Even an exact MDR-A/MDR-C pair can produce compatible pair evidence but cannot be accepted into one cluster under the cap. A violating proposal receives a hard constraint outcome and cannot publish. Review may resolve ambiguous identity evidence, but it cannot waive a hard cap through a normal membership override.

Proposed algorithm: maintain source-count summaries and supporting member identities with each proposed component, process candidate union proposals under a deterministic approved ordering, evaluate the complete constraint set before each union and retain accepted/rejected decisions. A single constrained union step is insufficient if partition processing later combines components; validate all cross-partition and final component unions as well. A deterministic ordering is reproducibility policy, not proof of globally optimal clustering. If several admissible allocations compete, route or resolve them under the declared conflict policy and show the evidence; do not silently choose an arbitrary winner.

25 5 Incremental repair concurrency and publication

Incremental additions reuse resident accepted evidence while re-evaluating affected pair policies and prospective cluster constraints. Serialize overlapping membership repairs with the existing component leases and expected membership revisions. Recheck counts against the latest accepted membership before commit; a stale count snapshot cannot authorize a second constrained-source member. Store count summaries with the same membership revision or recompute them during validation. The publication gate independently reconciles source counts and verifies every hard constraint on final memberships; no violating cluster is activated.

An approved policy change schedules impacted resident pair re-evaluation and cluster repair. A tightened cap may require split proposals; a loosened cap permits re-evaluation but does not automatically authorize a merge. Existing members may not be dropped merely to satisfy a count: preserve valid records as separate entities or hold the affected publication under an approved transition plan. Keep running batches pinned to their starting bundle while defining how the new release cuts over. If repair scope cannot be safely bounded, use a governed shadow rebuild. Recompute persistent IDs, survivor values, classification and downstream deltas through the existing identity policy.

Deletion excludes the source identity immediately, purges all historical evidence and derived values, then repairs the cluster and recalculates source counts. An accepted update to the same logical source identity replaces its active version without adding another member. Reinstatement or source-category changes remain subject to deletion watermarks, registry policy and revalidation. User configuration can add limits for a new source without deploying new matching or clustering code.

25 6 Configuration workflow and validation

Provide source-pair policy and cluster-constraint editors alongside the matching configuration workspace. The pair editor selects source selectors, attribute operands, exact/fuzzy comparators and mandatory versus qualifying groups. The constraint editor selects entity domain, trigger/source-presence condition, target source and maximum. Preview resolves the effective pair policy, shows per-condition evidence and computes prospective per-source counts. Explain a rejected merge with the configured source, count, maximum and rule revision. Validate conflicts and existing violations before controlled activation; keep draft saves, previews and operational calls within the internal service boundary.

Tests shall cover one constrained-source member with allowed fuzzy cross-source members; two constrained-source members with identical values; indirect bridges through multiple unconstrained sources; source-pair orientation; different field thresholds; mandatory gates versus general OR rules; replay and version updates; deletion; parallel attempts to add a second member; cross-partition unions; cap changes and backfills; and new configured sources/derived fields without code changes. Compare incremental and full-rebuild constraint outcomes under the same release. SP-01/02 map to source-pair policies and gates; SP-03/04 to prospective membership validation; SP-05 to release transitions, explanations and publication checks.
